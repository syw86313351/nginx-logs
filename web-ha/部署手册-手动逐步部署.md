## 第 4 步：写入 Keepalived 配置

### 4.1 健康检查脚本（两台一样）

这个脚本被 Keepalived 每 2 秒调用一次，检测本机 Nginx 是否正常。

```bash
cat > /etc/keepalived/check_nginx.sh << 'EOF'
#!/bin/bash
# ====================================================================
# Keepalived 健康检查 — Nginx 存活检测
# 返回值: 0 = 正常    非0 = 故障（停 keepalived，触发 VIP 漂移）
# ====================================================================

# 第一层: 进程检查 — Nginx 进程还在不在
if ! /usr/sbin/pidof nginx &>/dev/null; then
    # Nginx 进程不存在 → 本机已无法服务 → 停 keepalived → VIP 漂移到备机
    echo "$(date '+%Y-%m-%d %H:%M:%S'): Nginx 进程不存在，停 keepalived 触发 VIP 漂移" \
        >> /var/log/keepalived-check.log
    systemctl stop keepalived 2>/dev/null || true
    exit 1
fi

# 第二层: 端点检查 — Nginx 能否正常响应请求（比 pidof 更深入）
if command -v curl &>/dev/null; then
    if ! curl -sf --connect-timeout 2 http://127.0.0.1/health &>/dev/null; then
        # 第一次失败，等 1 秒再试（防止 Nginx 刚好在 reload 导致的瞬时不可用）
        sleep 1
        if ! curl -sf --connect-timeout 2 http://127.0.0.1/health &>/dev/null; then
            # 两次都失败 → 确认 Nginx 不可用 → 停 keepalived
            echo "$(date '+%Y-%m-%d %H:%M:%S'): /health 无响应，停 keepalived" \
                >> /var/log/keepalived-check.log
            systemctl stop keepalived 2>/dev/null || true
            exit 1
        fi
    fi
fi
exit 0
EOF

chmod +x /etc/keepalived/check_nginx.sh
```

### 4.2 守护脚本 + systemd timer（两台一样）

`check_nginx.sh` 把 Keepalived 停掉后，它自己就不会再跑了（是 Keepalived 在调它）。
所以需要这个独立脚本，每 30 秒检查：Nginx 恢复了没？恢复了就拉起 Keepalived。

```bash
# 写入守护脚本
cat > /usr/local/bin/nginx-watchdog.sh << 'EOF'
#!/bin/bash
# Nginx 恢复后自动拉起 Keepalived
if systemctl is-active --quiet keepalived; then
    exit 0
fi
if ! systemctl is-active --quiet nginx; then
    exit 0
fi
echo "$(date '+%Y-%m-%d %H:%M:%S'): Nginx 已恢复，重启 Keepalived" \
    >> /var/log/keepalived-watchdog.log
systemctl start keepalived
EOF

chmod +x /usr/local/bin/nginx-watchdog.sh

# 写入 systemd timer（每 30 秒执行一次）
cat > /etc/systemd/system/nginx-watchdog.service << 'EOF'
[Unit]
Description=Nginx 恢复后自动拉起 Keepalived

[Service]
Type=oneshot
ExecStart=/usr/local/bin/nginx-watchdog.sh
EOF

cat > /etc/systemd/system/nginx-watchdog.timer << 'EOF'
[Unit]
Description=每 30 秒检查一次 Nginx 是否恢复

[Timer]
OnBootSec=30
OnUnitActiveSec=30

[Install]
WantedBy=timers.target
EOF

systemctl daemon-reload
systemctl enable --now nginx-watchdog.timer
```

### 4.3 Keepalived 主配置

#### app10（MASTER）

```bash
cat > /etc/keepalived/keepalived.conf << 'EOF'
global_defs {
    router_id NGINX_HA_1           ! 本机唯一标识；MASTER 和 BACKUP 必须不同
    script_user root               ! 以 root 执行外部脚本
    enable_script_security         ! 启用脚本安全检查
}

vrrp_script chk_nginx {
    script      "/etc/keepalived/check_nginx.sh"   ! 健康检查脚本路径
    interval    2                                   ! 检查间隔（秒）；每 2 秒执行一次
    weight      -20                                 ! 故障时优先级减 20；100-20=80 < 90 → 触发切换
    fall        3                                   ! 连续失败 3 次才判定故障；2×3=6 秒容错
    rise        2                                   ! 连续成功 2 次才判定恢复；2×2=4 秒防抖
}

vrrp_instance VI_1 {
    state MASTER                    ! ★ VRRP 初始状态；MASTER 启动时抢占 VIP
    interface enp125s0f0-br0       ! 绑定网卡；VRRP 心跳和 VIP 都走这张网卡
    virtual_router_id 51           ! VRRP 路由器 ID；★ 主备必须一致
    priority 100                   ! ★ 优先级；100 > BACKUP的90
    advert_int 1                   ! 心跳间隔（秒）；备机 3 秒收不到即接管

    unicast_peer {                 ! 单播模式（比组播更可靠）
        192.168.131.10             ! app10 IP
        192.168.131.11             ! app11 IP
    }

    authentication {
        auth_type PASS             ! 认证类型
        auth_pass EctErp1234       ! ★ 主备必须一致
    }

    virtual_ipaddress {
        192.168.131.100/24 dev enp125s0f0-br0   ! VIP 地址
    }

    track_script {                 ! 绑定健康检查
        chk_nginx
    }

    notify_master "/bin/echo '\$(date): 晋升 MASTER' >> /var/log/keepalived-notify.log"
    notify_backup "/bin/echo '\$(date): 降级 BACKUP' >> /var/log/keepalived-notify.log"
    notify_fault  "/bin/echo '\$(date): FAULT!' >> /var/log/keepalived-notify.log"
}
EOF
```

## 第 5 步：写入 Nginx 配置（两台一样）

### 5.1 Nginx 主配置

```bash
# 先备份
cp /etc/nginx/nginx.conf /etc/nginx/nginx.conf.bak

# 写入优化后的主配置（每个参数后面都有 # 注释说明作用）
cat > /etc/nginx/nginx.conf << 'EOF'
user nginx;                                 # 运行用户，权限最小化，即使被入侵也只能访问 nginx 用户能访问的文件
worker_processes auto;                      # worker 进程数；auto = 自动匹配 CPU 核数，每个 worker 绑定一个核心
pid /run/nginx.pid;                         # 存储主进程 PID，用于 nginx -s reload/stop 等信号控制

events {
    worker_connections 32768;               # 每个 worker 最大连接数；总并发 = 32768 × worker_processes
    use epoll;                              # I/O 多路复用模型；epoll 是 Linux 下最高效的模型，高并发不线性下降
    multi_accept on;                        # 一次 accept() 尽可能多收新连接，减少系统调用，提升高并发吞吐
}

http {
    include /etc/nginx/mime.types;          # 加载文件扩展名 → Content-Type 映射表，确保浏览器正确识别文件类型
    default_type application/octet-stream;  # 未知后缀文件的默认 Content-Type，浏览器将提示下载而非尝试渲染

    sendfile on;                            # 零拷贝发送文件，内核直接磁盘 → socket，绕过用户态，大幅降低 CPU 占用
    tcp_nopush on;                          # 配合 sendfile，等数据积累再发包，减少 TCP 分段，大文件传输效率更高
    tcp_nodelay on;                         # 禁用 Nagle 算法，小包立即发送不等待合并，降低延迟，适合 REST API 场景

    # POST 用 keep-alive 复用连接，其他用 close 释放连接资源
    map $request_method $connection_type {
        default "close";                    # GET/PUT/DELETE 等请求使用短连接
        POST "keep-alive";                  # POST 请求使用长连接
    }

    keepalive_timeout 60s;                  # 浏览器空闲连接保持时间（秒）；60s 平衡了连接复用和资源释放
    keepalive_requests 10000;               # 单个 keep-alive 连接最多处理多少次请求后关闭，防止单连接长期占用
    client_body_timeout 1800s;              # 客户端发送 BODY 超时（上传文件时用，30分钟）；两次 write 之间超时返回 408
    client_header_timeout 1800s;            # 客户端发送 Header 超时（30分钟）；慢客户端超时返回 408
    send_timeout 1800s;                     # Nginx 向客户端发送响应的超时（30分钟）；两次 write 间隔超时则断开连接

    large_client_header_buffers 4 16k;      # 大 Header 缓冲（长 URL、大 Cookie 场景）；4×16KB=64KB，超出返回 414
    types_hash_max_size 2048;               # MIME 类型哈希表最大大小；值越大占内存越多，但类型查找越快
    server_names_hash_max_size 2048;         # 域名哈希表最大大小；多域名场景增大此值提升匹配速度
    server_names_hash_bucket_size 128;      # 域名哈希桶大小；域名特别长时需要增大，否则可能报错

    proxy_connect_timeout 3s;               # 连接后端 TCP 握手超时（秒）；3 秒连不上就切下一台 upstream 服务器
    proxy_read_timeout 5400s;               # 等待后端返回响应的超时（秒）；1.5 小时，覆盖长时间任务
    proxy_send_timeout 5400s;               # 向后端发送请求的超时（秒）；1.5 小时
    proxy_http_version 1.1;                 # 代理使用 HTTP/1.1 协议，支持与后端的 keep-alive 长连接
    proxy_set_header Connection "";         # 清除 Connection 头，让后端自行决定是否保持连接
    proxy_buffering off;                    # 关闭代理缓冲，后端响应直接流式转发给客户端

    client_max_body_size 1024m;             # 允许的请求体最大大小；1GB 覆盖大文件上传场景
    client_body_buffer_size 100m;           # 请求体内存缓冲区大小；小于 100MB 放内存，大于则写临时文件

    # 临时文件路径（多级目录，"1 2" = hash 1位一级目录 + 2位二级目录，防单目录文件过多）
    client_body_temp_path /data/nginx/body 1 2;             # 客户端请求体临时文件目录
    proxy_temp_path /data/nginx/tmp/proxy_temp 1 2;         # 代理临时文件目录
    fastcgi_temp_path /data/nginx/tmp/fastcgi_temp 1 2;     # FastCGI 临时文件目录
    uwsgi_temp_path /data/nginx/tmp/uwsgi_temp 1 2;         # uWSGI 临时文件目录
    scgi_temp_path /data/nginx/tmp/scgi_temp 1 2;           # SCGI 临时文件目录

    ssl_protocols TLSv1.2 TLSv1.3;          # 只启用安全的 TLS 版本；禁用 TLSv1.0/1.1（已被浏览器淘汰）
    ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256';  # 加密套件；ECDHE 前向加密 + AES-128-GCM
    ssl_prefer_server_ciphers on;           # 使用服务端加密套件优先级，防止客户端指定弱加密算法

    gzip on;                                # 开启压缩；文本类资源压缩后体积可减少 60-80%，节省带宽
    gzip_min_length 1k;                     # 小于 1KB 不压缩（压缩开销大于收益）
    gzip_comp_level 5;                      # 压缩级别 1-9；5 是 CPU 开销和压缩率的平衡点
    gzip_types text/plain text/css application/json application/javascript application/xml;  # 压缩的 MIME 类型

    # 禁止 IP 直接访问 — 检测 Host 头是否为 IP
    map $http_host $is_ip_access_by_host {
        default 0;                                          # 正常域名
        ~^[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+(:[0-9]+)?$ 1;    # IPv4 格式（可带端口）
        ~^\[.*\](:[0-9]+)?$ 1;                              # IPv6 格式（可带端口）
    }
    map $server_name $is_ip_access_by_name {
        default 0;                                          # 正常域名
        ~^[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+$ 1;               # IPv4 格式
        ~^\[.*\]$ 1;                                        # IPv6 格式
    }
    map "$is_ip_access_by_host:$is_ip_access_by_name" $is_ip_access {
        default 0;                                          # 正常域名访问
        "1:0" 1;                                            # Host 是 IP
        "0:1" 1;                                            # server_name 是 IP
        "1:1" 1;                                            # 两者都是 IP
    }

    # 通用日志
    log_format main '$remote_addr - - [$time_local] "$request" $status '
                    '$body_bytes_sent "$http_referer" "$http_user_agent"';
    # 长连接(POST)日志 — 含 upstream 和性能数据
    log_format long_connection
        '$remote_addr - $remote_user [$time_local] '
        '"$request" $status $body_bytes_sent '
        '"$http_referer" "$http_user_agent" '
        '"$http_x_forwarded_for" '
        'connection_type="long" '
        'connection="$connection" '
        'request_method="$request_method" '
        'upstream_addr="$upstream_addr" '
        'upstream_status="$upstream_status" '
        'upstream_response_time="$upstream_response_time" '
        'request_time="$request_time"';
    # 短连接日志
    log_format short_connection
        '$remote_addr - $remote_user [$time_local] '
        '"$request" $status $body_bytes_sent '
        '"$http_referer" "$http_user_agent" '
        '"$http_x_forwarded_for" '
        'connection_type="short" '
        'connection="$connection" '
        'upstream_addr="$upstream_addr" '
        'upstream_status="$upstream_status" '
        'upstream_response_time="$upstream_response_time" '
        'request_time="$request_time"';

    access_log /data/nginx/logs/access.log main;            # 访问日志路径和格式
    error_log  /data/nginx/logs/error.log warn;             # 错误日志路径和级别

    # 默认 server — 拒绝未匹配域名 / IP 直接访问
    server {
        listen 80 default_server;                           # HTTP 默认端口
        listen 443 ssl default_server;                      # HTTPS 默认端口
        server_name _;                                      # 匹配所有请求（兜底）

        ssl_certificate /data/ssl/zncmjt.com/fullchain.pem;         # SSL 证书文件
        ssl_certificate_key /data/ssl/zncmjt.com/privkey.pem;       # SSL 私钥文件

        if ($is_ip_access = 1) {                            # IP 直接访问 → 403 Forbidden
            return 403;
        }
        if ($http_host = "") {                              # 无 Host 头 → 403
            return 403;
        }
        return 404;                                         # 未识别域名 → 404 Not Found
    }

    include /etc/nginx/conf.d/*.conf;                       # 加载站点配置
}
EOF
```

### 5.2 后端服务器池

```bash
cat > /etc/nginx/conf.d/upstream.conf << 'EOF'
upstream backend_pool {
    least_conn;                                             # 最少连接算法：请求分给当前连接数最少的后端
    server 192.168.1.10:8080 max_fails=3 fail_timeout=30s;  # 后端 Tomcat 1；连续失败 3 次标记不可用，30 秒后重试
    server 192.168.1.11:8080 max_fails=3 fail_timeout=30s;  # 后端 Tomcat 2
    keepalive 32;                                           # 与后端保持 32 个空闲长连接，减少 TCP 握手
}
EOF
```

### 5.3 反向代理 + 健康检查

```bash
cat > /etc/nginx/conf.d/virtual-host.conf << 'EOF'
server {
    listen 80;                                              # 监听 HTTP 端口
    server_name _;                                          # 匹配所有域名
    access_log /var/log/nginx/ha-access.log;                # 访问日志（独立于默认日志）
    error_log  /var/log/nginx/ha-error.log warn;            # 错误日志

    # 健康检查端点 — Keepalived 每 2 秒请求此 URL 判断 Nginx 是否存活
    location = /health {
        access_log off;                                     # 不记录健康检查到访问日志，避免日志膨胀
        return 200 "OK\n";                                  # 返回纯文本 OK
        add_header Content-Type text/plain;
    }

    # 反向代理 — 将请求转发到 upstream backend_pool
    location / {
        proxy_pass http://backend_pool;                     # 转发到后端 Tomcat 服务器池
        proxy_http_version 1.1;                             # 使用 HTTP/1.1 支持长连接

        proxy_set_header Host              $host;           # 透传原始域名

        proxy_read_timeout    60s;                          # 等待后端响应超时

}
EOF
```

### 5.5 后端 Tomcat 健康检测（自动 up/down）

Nginx 自带的被动健康检查只在请求失败后才标记——第一个失败请求用户会看到错误。
这个脚本主动每 10 秒探测一次后端，提前知道状态，自动从 upstream 里摘掉故障节点。

```bash
# 写入检测脚本
cat > /usr/local/bin/upstream-health-check.sh << 'SCRIPT'
#!/bin/bash
# 每 10 秒探测后端 Tomcat，自动更新 upstream 配置

UPSTREAM_CONF="/etc/nginx/conf.d/upstream.conf"
UPSTREAM_STATE="/var/run/nginx-upstream.state"

BACKENDS=(
    "192.168.1.10:8080|/xxx/html/base/page/healthz.txt"   # Tomcat 1: IP:PORT|健康检查路径
    "192.168.1.11:8080|/xxx/html/base/page/healthz.txt"   # Tomcat 2
)

check_backend() {
    local addr="$1"
    local path="$2"
    local ip="${addr%:*}"
    local port="${addr#*:}"
    timeout 2 bash -c "echo > /dev/tcp/$ip/$port" 2>/dev/null && return 0
    curl -sf --connect-timeout 3 "http://${addr}${path}" &>/dev/null && return 0
    return 1
}

STATE=""
for backend in "${BACKENDS[@]}"; do
    addr="${backend%%|*}"
    path="${backend#*|}"
    if check_backend "$addr" "$path"; then
        STATE+="${addr}:UP"$'\n'
    else
        STATE+="${addr}:DOWN"$'\n'
    fi
done

# 状态没变就不 reload，避免频繁刷
if [ -f "$UPSTREAM_STATE" ] && [ "$(cat "$UPSTREAM_STATE")" = "$STATE" ]; then
    exit 0
fi

# 重建 upstream 配置
cat > "$UPSTREAM_CONF" << 'HEADER'
upstream backend_pool {
    least_conn;
HEADER
for backend in "${BACKENDS[@]}"; do
    addr="${backend%%|*}"
    if echo "$STATE" | grep -q "^${addr}:UP$"; then
        echo "    server $addr max_fails=1 fail_timeout=10s;  # UP" >> "$UPSTREAM_CONF"
    else
        echo "    server $addr max_fails=1 fail_timeout=10s down;  # DOWN" >> "$UPSTREAM_CONF"
    fi
done
cat >> "$UPSTREAM_CONF" << 'FOOTER'
    keepalive 32;
}
FOOTER

echo "$STATE" > "$UPSTREAM_STATE"
nginx -t &>/dev/null && nginx -s reload 2>/dev/null
SCRIPT

chmod +x /usr/local/bin/upstream-health-check.sh

# systemd timer — 每 10 秒执行一次
cat > /etc/systemd/system/upstream-health-check.service << 'EOF'
[Unit]
Description=Tomcat 后端健康检测，自动更新 Nginx upstream

[Service]
Type=oneshot
ExecStart=/usr/local/bin/upstream-health-check.sh
EOF

cat > /etc/systemd/system/upstream-health-check.timer << 'EOF'
[Unit]
Description=每 10 秒检测一次 Tomcat 后端状态

[Timer]
OnBootSec=30
OnUnitActiveSec=10

[Install]
WantedBy=timers.target
EOF

systemctl daemon-reload
systemctl enable --now upstream-health-check.timer
```

**效果：** Tomcat 重启期间 → 脚本检测到不可达 → upstream 自动标 `down` → Nginx 不往那台发请求 → Tomcat 启动完 → 脚本检测到恢复 → 自动去掉 `down`。

### 7.7 故障排查：SENTINEL FAILOVER 返回 NOGOODSLAVE

**症状：** `SENTINEL FAILOVER redis-ha` 返回 `NOGOODSLAVE No suitable replica to promote`，同时某个 Sentinel 的 `SENTINEL SLAVES redis-ha` 显示 slave 的 `flags` 包含 `s_down`。

**根因：** Sentinel 运行时会把自己的状态写回 `sentinel.conf`。如果在 `replica-announce-ip` 配置好之前 Sentinel 就已经启动，它可能缓存了 Docker 内部 IP（如 172.17.0.x）的旧 slave 信息。之后即使 slave 配置了正确的 `replica-announce-ip`，Sentinel 可能仍保留着旧条目，导致远程仲裁机把 slave 标为 `s_down`。当仲裁机的 Sentinel 被选为故障切换 leader 时，它找不到健康的 slave，返回 NOGOODSLAVE。

**解决方案：干净重启所有 Sentinel**

```bash
# ★ 在所有三台机器上都要执行（app10、app11、仲裁机）

# ── 第 1 步：在 app10 上 ──
cd /opt/redis-ha
docker compose down          # 停 Redis + Sentinel
cat > /opt/redis-ha/sentinel.conf << 'EOF'
sentinel monitor redis-ha 192.168.131.10 6379 2
sentinel auth-pass redis-ha cns@2035
sentinel down-after-milliseconds redis-ha 2000
sentinel failover-timeout redis-ha 20000
sentinel parallel-syncs redis-ha 1
sentinel known-replica redis-ha 192.168.131.11 6379
sentinel known-replica redis-ha 192.168.131.10 6379
EOF
docker compose up -d         # 启动（自动写入干净状态）

# ── 第 2 步：在 app11 上 ──
cd /opt/redis-ha
docker compose down          # 停 Redis + Sentinel
cat > /opt/redis-ha/sentinel.conf << 'EOF'
sentinel monitor redis-ha 192.168.131.10 6379 2
sentinel auth-pass redis-ha cns@2035
sentinel down-after-milliseconds redis-ha 2000
sentinel failover-timeout redis-ha 20000
sentinel parallel-syncs redis-ha 1
sentinel known-replica redis-ha 192.168.131.11 6379
sentinel known-replica redis-ha 192.168.131.10 6379
EOF
docker compose up -d         # 启动
sleep 3
# ★ 重新注册 slave
docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning REPLICAOF 192.168.131.10 6379

# ── 第 3 步：在仲裁机上 ──
cd /opt/redis-ha-sentinel
docker compose down          # 停 Sentinel
cat > /opt/redis-ha-sentinel/sentinel.conf << 'EOF'
sentinel monitor redis-ha 192.168.131.10 6379 2
sentinel auth-pass redis-ha cns@2035
sentinel down-after-milliseconds redis-ha 2000
sentinel failover-timeout redis-ha 20000
sentinel parallel-syncs redis-ha 1
sentinel known-replica redis-ha 192.168.131.11 6379
sentinel known-replica redis-ha 192.168.131.10 6379
EOF
docker compose up -d         # 启动

# ── 第 4 步：验证（在任何一台机器上）──
# 1. 主从状态
ssh app10 "docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning ROLE"
# 预期: master
ssh app11 "docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning ROLE"  
# 预期: slave

# 2. Sentinel 看到的主从信息
docker exec sentinel-ha redis-cli -p 26379 SENTINEL MASTER redis-ha | grep -E "ip|flags|num-slaves"
# flags: master, num-slaves: 1

docker exec sentinel-ha redis-cli -p 26379 SENTINEL SLAVES redis-ha | grep -E "ip|flags|master-link"
# ip: 192.168.131.11, flags: slave, master-link-status: ok
# ★ 关键: flags 不能包含 s_down，master-link-status 必须是 ok

# 3. 仲裁机也确认 slave 健康
docker exec redis-ha-sentinel redis-cli -p 26379 SENTINEL SLAVES redis-ha | grep -E "ip|flags"
# flags 不能包含 s_down

# 4. CKQUORUM — 必须有 3 个可用的 Sentinel
docker exec sentinel-ha redis-cli -p 26379 SENTINEL CKQUORUM redis-ha
# 预期: OK 3 usable Sentinels. Quorum and failover authorization can be reached

# 5. 手动触发故障切换
docker exec sentinel-ha redis-cli -p 26379 SENTINEL FAILOVER redis-ha
# 预期: OK
# ★ 3-6 秒后 Slave 被提升为 Master
```

**为什么需要 `docker compose down` 而不是 `restart`：**
- `restart` 保留卷挂载，Sentinel 启动时读到旧的运行时状态（含错误的 IP）
- `down` 清除容器，但旧的 sentinel.conf 里还有 Sentinel 自动写入的状态
- 所以先 `down`，再重写干净的 sentinel.conf，最后 `up -d`——确保 Sentinel 从零开始

### 7.10 脑裂（Split-Brain）处理

#### 什么是脑裂

脑裂是指集群中同时存在两个 Master，两边都认为自己可以接受写入。这会导致**数据不一致**——同一个 key 在两边有不同的值，一旦合并必然丢一边的数据。

最终应该只有一个 Master。本方案中 app10 的 `replica-priority=100` 高于 app11 的 `replica-priority=50`，因此始终保留 **app10** 的数据，丢弃 app11 的。

#### 何时会发生

| 场景 | 原因 |
|------|------|
| Sentinel 未生效 | NOGOODSLAVE 导致故障切换失败，app10 宕机期间 app11 没有自动提升，手动重启 app10 后两边都是 master |
| app11 重启后丢失 slave 身份 | Sentinel 在 app11 重启期间没来得及下发 SLAVEOF 命令 |
| 网络分区 | app10 和 app11 之间网络断开，但各自和 Sentinel 的通信正常（极少见，需要多网络故障叠加） |
| 三台 Sentinel 全部宕机 | 没有 Sentinel 管理主从关系，任何 Redis 重启都可能以 master 身份启动 |

#### 第一步：发现脑裂

```bash
# 在 app10 上
docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning ROLE
# 输出: master  ← 自称 Master

# 在 app11 上
docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning ROLE
# 输出: master  ← 也自称 Master

# ★ 两者都是 master = 脑裂确认
```

也可以用 Sentinel 的视角确认：

```bash
# 在仲裁机上，看 Sentinel 认为谁是 Master
docker exec redis-ha-sentinel redis-cli -p 26379 SENTINEL MASTER redis-ha | grep -E "ip|flags"

# 如果 flags 不是 master 或者 ip 和你预期不一样 → Sentinel 状态也混乱了
# 如果 flags=master 且 ip 正确（比如 192.168.131.11）→ Sentinel 正常，只是 app10 没被降级
```

#### 第二步：判断保留哪边的数据

**原则：保留有最新业务数据的 Master。**

| 判断依据 | 保留哪边 |
|----------|---------|
| 正常故障切换后（app10 宕机 → app11 接管） | **app11** — 宕机期间 app11 接收了所有写入 |
| app10 只是短暂重启，没有业务写入 | **app10** — replica-priority 高，数据最全 |
| 不确定哪边数据更新 | 查两边的 key 数量: `DBSIZE`，保留多的那边 |
| app10 是原始 Master，宕机时间很短 | **app10** — 数据最完整 |

**检查数据量辅助判断：**

```bash
# 在 app10 上
docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning DBSIZE

# 在 app11 上
docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning DBSIZE

# 对比两边的 key 数量，结合宕机时间判断谁的数据更新
```

#### 第三步：手动修复（推荐方案：保留 app10）

下面以**保留 app10 数据，丢弃 app11 数据**为例：

```bash
# ── 1. 停 app11 Redis ──
ssh app11 "cd /opt/redis-ha && docker compose stop redis"

# ── 2. 清空 app11 的旧数据（全量同步不需要，但如果想彻底干净就清）──
ssh app11 "rm -rf /opt/redis-ha/redis-data/*"

# ── 3. 确认 app10 是 Master ──
ssh app10 "docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning ROLE"
# 预期: master

# ── 4. 启动 app11 Redis ──
ssh app11 "cd /opt/redis-ha && docker compose start redis"

# ── 5. 立即注册 app11 为 Slave ──
ssh app11 "docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning REPLICAOF 192.168.131.10 6379"

# ── 6. 验证主从同步 ──
sleep 3
ssh app11 "docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning INFO replication | grep master_link_status"
# 预期: master_link_status:up

# ── 7. 验证 Sentinel 集群 ──
# 三台 Sentinel 都正确指向 app10 为 Master
docker exec sentinel-ha redis-cli -p 26379 SENTINEL MASTER redis-ha | grep -E "ip|flags|num-slaves"
# 预期: ip=192.168.131.10, flags=master, num-slaves=1
```

**如果保留 app11 数据（app10 宕机期间 app11 已接管生产写入）：**

```bash
# ── 1. 在 app10 上手动降级 ──
ssh app10 "docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning REPLICAOF 192.168.131.11 6379"

# ── 2. 验证 ──
ssh app10 "docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning ROLE"
# 预期: slave
```

**注意：** REPLICAOF 会触发全量同步，app10 的旧数据被 app11 覆盖。如果 app10 上有需要保留的数据，先用 `BGSAVE` 导出到 RDB 文件再操作。

#### 第四步：修复 Sentinel（如果 Sentinel 状态也乱了）

修复主从关系后，如果 Sentinel 仍指向错误的 Master：

```bash
# 选项 A — 单台 Sentinel 重置（轻量，单台状态不对时用）
# 在状态异常的 Sentinel 上执行：
docker exec sentinel-ha redis-cli -p 26379 SENTINEL RESET redis-ha
# 警告: RESET 会清空 known-replica，需要重启 Sentinel 从配置文件重新加载
docker compose restart sentinel
# 这样 Sentinel 会重新发现集群，自动纠正

# 选项 B — 全部干净重启（彻底，所有 Sentinel 都乱了时用）
# 详见 7.7 节流程: docker compose down → 重写 sentinel.conf → up -d
```

#### 预防措施

| 措施 | 说明 |
|------|------|
| `--replica-priority 100/50` | 确保 app10 始终优先被选为 Master，避免来回切换 |
| `--replica-announce-ip` | 明确宣告 IP，防止 Sentinel 拿到 Docker 内部地址而无法管理 |
| `sentinel known-replica` | 直接告诉 Sentinel Slave 位置，不依赖 Master INFO 输出 |
| `network_mode: host` | 避免 Docker NAT 导致的 IP 混乱 |
| Docker `restart: always` | 宿主机重启后 Redis 和 Sentinel 自动恢复 |
| 三个 Sentinel + quorum=2 | 任意一台 Sentinel 挂掉不影响集群管理 |

#### 预防性监控脚本

部署到 app10 和 app11 上，每 30 秒检查一次是否脑裂：

```bash
cat > /usr/local/bin/check-split-brain.sh << 'SCRIPT'
#!/bin/bash
# 脑裂检测: 如果本机自称 master，且另一台也是 master → 告警

ROLE=$(docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning ROLE 2>/dev/null | head -1)

if [ "$ROLE" != "master" ]; then
    exit 0   # 我是 slave，正常
fi

# 我是 master，检查对方是不是也自称 master
LOCAL_IP=$(hostname -I | awk '{print $1}')
if [ "$LOCAL_IP" = "192.168.131.10" ]; then
    PEER="192.168.131.11"
else
    PEER="192.168.131.10"
fi

PEER_ROLE=$(ssh -o ConnectTimeout=3 -o StrictHostKeyChecking=no $PEER \
    "docker exec redis-ha redis-cli -a cns@2035 --no-auth-warning ROLE 2>/dev/null" 2>/dev/null | head -1)

if [ "$PEER_ROLE" = "master" ]; then
    echo "$(date '+%Y-%m-%d %H:%M:%S'): ⚠️ 脑裂！$LOCAL_IP 和 $PEER 都是 Master！" \
        >> /var/log/split-brain.log
fi
SCRIPT

chmod +x /usr/local/bin/check-split-brain.sh

# systemd timer — 每 30 秒检查一次
cat > /etc/systemd/system/check-split-brain.service << 'EOF'
[Unit]
Description=Redis 脑裂检测

[Service]
Type=oneshot
ExecStart=/usr/local/bin/check-split-brain.sh
EOF

cat > /etc/systemd/system/check-split-brain.timer << 'EOF'
[Unit]
Description=每 30 秒检测一次 Redis 脑裂

[Timer]
OnBootSec=60
OnUnitActiveSec=30

[Install]
WantedBy=timers.target
EOF

systemctl daemon-reload
systemctl enable --now check-split-brain.timer
```

#### 第五步：预防脑裂（主动规避）

监控脚本只能**发现**脑裂，下面的措施让脑裂**不发生**。

##### 方案 A：init-guard 容器（已内置，无需额外部署）

**docker-compose.yml 已内置！** 两台机器的 docker-compose 里都有 `init-guard` 容器，`docker compose up -d` 时自动执行。

核心原则：**Redis 启动后，先问 Sentinel 集群里是否已经有 Master。如果有且不是自己，立刻以 Slave 身份加入。** 这就是"后启动的默认当 slave"——但通过 Sentinel 来判断，而不是写死 `--replicaof`。

> **为什么不能用 `--replicaof` 写死在 docker-compose 里：** Sentinel 提升 Slave 为 Master 时发的是 `REPLICAOF NO ONE`，只改运行时状态。下次容器重启，命令行的 `--replicaof` 还在，刚被提升的 Master 又回去当 Slave——结果两个都是 Slave，集群没有 Master。

**无需额外部署。** `docker compose up -d` 时 init-guard 容器自动执行以下逻辑：

```
Redis 就绪 → Sentinel 就绪 → init-guard 启动
  ↓
  问本地 Sentinel: "现在谁是 Master？"
  ↓
  Master IP ≠ 本机 IP → REPLICAOF Master_IP 6379 → 本机成为 Slave
  Master IP = 本机 IP  → 保持不变
  ↓
init-guard 退出 (restart: "no"), 不会再次运行
```

**两种典型场景：**

```
场景 1 — app10 正常运行，app11 重启：
  app11 init-guard → 问 Sentinel → "Master 是 192.168.131.10"
  → ≠ 本机 192.168.131.11 → REPLICAOF 192.168.131.10 6379
  → ✅ app11 当 Slave

场景 2 — 故障切换后 app10 重启：
  app10 之前挂了，app11 被 Sentinel 提升为 Master
  app10 init-guard → 问 Sentinel → "Master 是 192.168.131.11"
  → ≠ 本机 192.168.131.10 → REPLICAOF 192.168.131.11 6379
  → ✅ app10 当 Slave，脑裂不会发生
```

查看 init-guard 执行日志：

```bash
docker logs $(docker ps -a --filter "name=init-guard" --format "{{.ID}}" | head -1)
```

##### 方案 B：Redis 写入保护（可选，适合强一致性场景）

如果业务允许在 Slave 断连时**短暂拒绝写入**（比如金融交易），可以开启 Redis 的写入保护。当 Master 检测不到 Slave 时，自动拒绝所有写操作，从根源上杜绝脑裂期间的数据分歧。

**注意：** 这对 Session 管理通常不合适——Slave 重启维护期间用户无法登录。按需开启。

```bash
# 在 docker-compose.yml 的 redis-server 启动参数中追加：
#   --min-replicas-to-write 1
#   --min-replicas-max-lag 10
```

| 参数 | 作用 | 副作用 |
|------|------|--------|
| `min-replicas-to-write 1` | 至少 1 个 Slave 在线才接受写入 | Slave 宕机/维护时整个 Redis 只读 |
| `min-replicas-max-lag 10` | Slave 复制延迟超过 10 秒也拒绝写入 | 网络抖动时短暂不可写 |

##### 方案 C：Sentinel 存活监控（两台都部署）

脑裂的根因往往是 Sentinel 没有正常工作。这个脚本监控 Sentinel 进程，挂了立即告警并尝试重启。

```bash
cat > /usr/local/bin/sentinel-watchdog.sh << 'SCRIPT'
#!/bin/bash
# Sentinel 存活监控 — 挂了立即重启

if docker exec sentinel-ha redis-cli -p 26379 PING &>/dev/null; then
    exit 0
fi

echo "$(date): ⚠️ Sentinel 无响应，尝试重启..." >> /var/log/sentinel-watchdog.log
cd /opt/redis-ha && docker compose restart sentinel

sleep 5
if docker exec sentinel-ha redis-cli -p 26379 PING &>/dev/null; then
    echo "$(date): Sentinel 已恢复" >> /var/log/sentinel-watchdog.log
else
    echo "$(date): ❌ Sentinel 重启失败！" >> /var/log/sentinel-watchdog.log
fi
SCRIPT

chmod +x /usr/local/bin/sentinel-watchdog.sh

cat > /etc/systemd/system/sentinel-watchdog.service << 'EOF'
[Unit]
Description=Sentinel 存活监控

[Service]
Type=oneshot
ExecStart=/usr/local/bin/sentinel-watchdog.sh
EOF

cat > /etc/systemd/system/sentinel-watchdog.timer << 'EOF'
[Unit]
Description=每 30 秒检查一次 Sentinel 是否存活

[Timer]
OnBootSec=30
OnUnitActiveSec=30

[Install]
WantedBy=timers.target
EOF

systemctl daemon-reload
systemctl enable --now sentinel-watchdog.timer
```

##### 各方案对比

| 方案 | 防护层级 | 适用场景 | 部署要求 |
|------|---------|---------|---------|
| **A: init-guard 容器** ★ | Redis 启动时角色自检 | 已内置，防重启后脑裂 | docker-compose 自带 |
| B: 写入保护 | 拒绝脑裂期间的写入 | 强一致性业务（非 Session） | 按需 |
| C: Sentinel 监控 | Sentinel 挂了自动重启 | 可选，额外保险 | app10 + app11 |
| 脑裂检测（上文） | 30 秒周期扫描 | 可选 | app10 + app11 |

> **注意**: `context.xml` 里 `configPath` 要写**容器内路径** `/usr/local/tomcat/conf/redisson.yaml`，不是宿主机路径。
